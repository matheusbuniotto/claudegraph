# Airflow and LangGraph: Core Execution Machinery (Graph / DAG / State Machine)

Scope: the execution cores of Apache Airflow and LangGraph — scheduling, state transitions, and data flow — with the UI/webserver layers deliberately excluded. All claims are pinned to the versions verified below and cited inline to the source that owns them.

**Version pins.**
- **Airflow:** source-level claims verified against tag **`2.10.5`** of `apache/airflow` (`https://raw.githubusercontent.com/apache/airflow/2.10.5/...`); docs claims cite the 2.10.5 docs pages where they exist. Note: the `stable` docs at airflow.apache.org now describe **Airflow 3.x** (Task SDK, `airflow.sdk`, supervisor process, `awaiting_input` state, dag bundles) — none of which exist at 2.10.5 [source: https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html]. Where 2.10.5 diverges from 3.x, this document says so explicitly.
- **LangGraph:** source-level claims verified against `main` of `langchain-ai/langgraph`, cross-checked against the released PyPI sdist **langgraph 1.2.11**. Module paths below are relative to `libs/langgraph/langgraph/` in that repo unless noted. Docs host used: `docs.langchain.com/oss/python/langgraph/` (the legacy host `langchain-ai.github.io/langgraph` redirects there) [source: https://langchain-ai.github.io/langgraph/concepts/low_level/].
- Structural note: on current LangGraph `main`, checkpointing ships in the separate **`langgraph-checkpoint`** package (monorepo path `libs/checkpoint/langgraph/checkpoint/`) [source: https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/pyproject.toml].

### 1.2 The DAG as a graph

**Structure storage — plain sets, no bitsets.** `DAG.__init__` creates `self.task_dict: dict[str, Operator]` [source: airflow/models/dag.py:613 @ 2.10.5]; `DAG.tasks` returns `list(self.task_dict.values())` and `task_ids` lists the keys. Edges are **plain `set[str]` of node ids** declared on `DAGNode` (`airflow.models.taskmixin`): `upstream_task_ids` and `downstream_task_ids` [source: airflow/models/taskmixin.py:173–174 @ 2.10.5]. Bitset dependency encoding was removed in Airflow 2.0; 2.10.5 uses sets. Edges are created in `DAGNode._set_relatives` (~line 230): for the upstream case it does `task.downstream_task_ids.add(self.node_id); self.upstream_task_ids.add(task.node_id)`, mirrored for downstream. `set_upstream`/`set_downstream` and the bitshift operators `__lshift__`/`__rshift__`/`__rrshift__` all funnel into `_set_relatives` [source: airflow/models/taskmixin.py @ 2.10.5]. **`DAG.add_edge` does not exist at 2.10.5**; `DAG.add_task` assigns default `start_date` from the DAG and registers the task via `add_tasks` → `task_dict` [source: airflow/models/dag.py:2813, 2858 @ 2.10.5]. `downstream_list` = `[self.dag.get_task(tid) for tid in self.downstream_task_ids]` [source: airflow/models/taskmixin.py:278 @ 2.10.5].

**Topological order and cycle detection.** `DAG.topological_sort()` (dag.py:2360) returns a `tuple` of tasks in topological order ("a task comes after any of its upstream dependencies"); it is **deprecated** in favor of `TaskGroup.topological_sort`, which it delegates to (flattening nested TaskGroups). Cycle detection: `check_cycle` from `airflow.utils.dag_cycle_tester` runs on the DAG and raises `AirflowDagCycleException` [source: airflow/models/dag.py:2360–2375, 2952; airflow/utils/task_group.py:500, 554 @ 2.10.5].

**`DAG.get_task_instances()`** (dag.py:1869) — `(self, start_date=None, end_date=None, state=None, session=NEW_SESSION) -> list[TaskInstance]`, defaulting start_date to 30 days back and ordering by `DagRun.execution_date`. The scheduler hot path instead uses `DagRun.get_task_instances` (dagrun.py:617) and `DagRun.task_instance_scheduling_decisions` (dagrun.py:966) [source: airflow/models/dagrun.py @ 2.10.5].

**Runtime dependency checking** for a TI is the `ti_deps` system: `TI.are_dependencies_met(dep_context, session)` iterates `dep_context.deps | self.task.deps` via `get_failed_dep_statuses` [source: airflow/models/taskinstance.py:2586 @ 2.10.5].

**The scheduler loop** (class `SchedulerJobRunner(BaseJobRunner)`, `airflow/jobs/scheduler_job_runner.py`):

- `_run_scheduler_loop()` (line 1057): per its docstring — "Harvest DAG parsing results through DagFileProcessorAgent → Find and queue executable tasks (change TI state in DB, queue tasks in executor) → Heartbeat executor (execute queued tasks asynchronously, sync on running-task states)". It registers `EventScheduler` timers (`adopt_or_reset_orphaned_tasks`, `check_trigger_timeouts`, `_emit_pool_metrics`, `_find_and_purge_zombies`, `_update_dag_run_state_for_paused_dags`, `_handle_tasks_stuck_in_queued`) and loops forever [source: airflow/jobs/scheduler_job_runner.py:1057–1140 @ 2.10.5].
- `_do_scheduling(session)` (line 1211): (1) create necessary DagRuns by examining `next_dagrun_create_after` of `DagModel` (bounded by `scheduler.max_dagruns_to_create_per_loop`); (2) find the "next n oldest" **running** DagRuns to examine (`scheduler.max_dagruns_per_loop_to_schedule`, default 20, rows selected with row locks); (3) via a **Critical Section**, queue tasks and send them to the executor. It calls `_create_dagruns_for_dags`, `_start_queued_dagruns` (queued DagRuns → running), `_get_next_dagruns_to_examine(RUNNING)`, `_schedule_all_dag_runs`, then `_critical_section_enqueue_task_instances`; short-circuits if `sum(executor.slots_available) <= 0`; a lock-not-available `OperationalError` means another scheduler holds the critical section → rollback, return 0 [source: airflow/jobs/scheduler_job_runner.py:1211–1303 @ 2.10.5].
- **Critical section** — `_critical_section_enqueue_task_instances` (line 703): "a 'critical section' meaning that only a single scheduler process can execute this function at the same time… achieved by doing `SELECT … from pool FOR UPDATE`. For DBs that support NOWAIT, a 'blocked' scheduler will skip this and continue". It computes `max_tis = min(max_tis_per_query, core.parallelism − occupied_slots)` and delegates to `_executable_task_instances_to_queued` + `_enqueue_task_instances_with_queued_state`. On PostgreSQL the lock is also an advisory lock (`pg_try_advisory_xact_lock(DBLocks.SCHEDULER_CRITICAL_SECTION)`) [source: airflow/jobs/scheduler_job_runner.py:310–360, 703–760 @ 2.10.5; https://airflow.apache.org/docs/apache-airflow/2.10.5/administration-and-deployment/scheduler.html].
- `_executable_task_instances_to_queued(max_tis, session)` (line 310): picks TIs "ready for execution" respecting pool limits, DAG `max_active_tasks`, executor state, priority, per-DAG/per-run active-TI limits. It obtains `Pool.slots_stats(lock_rows=True)` (the `FOR UPDATE`), bails if no free pool slots, then bulk-updates the chosen TIs to `QUEUED`: `update(TI).values(state=QUEUED, queued_dttm=now, queued_by_job_id=self.job.id)` [source: airflow/jobs/scheduler_job_runner.py:640–665 @ 2.10.5].
- `_enqueue_task_instances_with_queued_state(tis, executor, session)` (line 670): per TI builds `ti.command_as_list(local=True, pickle_id=ti.dag_model.pickle_id)` and calls `executor.queue_command(ti, command, priority=ti.priority_weight, queue=ti.queue)` [source: airflow/jobs/scheduler_job_runner.py:670–700 @ 2.10.5].
- **DagRun creation:** scheduler calls `dag.create_dagrun(state, execution_date, run_id, start_date, external_trigger, conf, run_type, …, data_interval, …)` (dag.py:3098; call sites scheduler_job_runner.py:1371, 1483). `DagRunType` (`airflow/utils/types.py:75`) = `backfill | scheduled | manual | dataset_triggered`; `generate_run_id()` = `f"{run_type}__{logical_date.isoformat()}"` [source: airflow/utils/types.py @ 2.10.5].
- `DagRun.schedule_tis(schedulable_tis, session, max_tis_per_query)` (dagrun.py:1550): sets TIs to **SCHEDULED** via bulk `update(TI).values(state=SCHEDULED, try_number=case(...))`. Special cases: tasks that `inherits_from_empty_operator` with no callbacks/outlets are kept in a "dummy" list (later set straight to SUCCESS); tasks with `start_trigger_args` and `start_from_trigger=True` are deferred directly from the scheduler; otherwise appended to `schedulable_ti_ids` [source: airflow/models/dagrun.py:1550–1615 @ 2.10.5].
- **DAG file parsing:** `DagFileProcessorAgent` supervises per-file `DagFileProcessorProcess` subprocesses; the scheduler reads **serialized DAGs** from the `serialized_dag` table, not the files (hence "DAG '%s' not found in serialized_dag table" logs in `_do_scheduling`) [source: airflow/dag_processing/manager.py:104, 249; processor.py:94; models/dagbag.py:206–623 @ 2.10.5].
- **DagRun state rollup:** `DagRun.update_state` (dagrun.py:760) computes run state from **leaf** TIs (`leaf_tis = {ti for ti in tis if ti.task_id in leaf_task_ids if ti.state != REMOVED}`): the run is `success` if all leaves are success/skipped, `failed` if any leaf is failed/upstream_failed [source: airflow/models/dagrun.py @ 2.10.5; https://airflow.apache.org/docs/apache-airflow/2.10.5/core-concepts/dag-run.html].

**Executor cycle** (`airflow.executors.base_executor.BaseExecutor`, base_executor.py:110). Core state: `self.queued_tasks: dict[TaskInstanceKey, QueuedTaskInstanceType]`, `self.running: set[TaskInstanceKey]`, `self.event_buffer: dict[TaskInstanceKey, EventBufferValueType]` (lines 135–137) [source: airflow/executors/base_executor.py @ 2.10.5].

- `queue_command(task_instance, command, priority=1, queue=None)` (line 160): stores `queued_tasks[key] = (command, priority, queue, task_instance)` unless already queued.
- `heartbeat()` (line 233): emits metrics (`open_slots`, `num_running_tasks`, `num_queued_tasks`), then `self.sync()` and `self.trigger_tasks(open_slots)`.
- `sync()` (line 225): base **no-op** — "Executors should override this to perform gather statuses."
- `trigger_tasks(open_slots)` (line 326): orders the queue by priority (`order_queued_tasks_by_priority`, line 313), pops up to `open_slots` items, guards against re-triggering keys still in `self.running` (retry-race guard for deferred tasks), then `_process_tasks` → `self.execute_async(key, command, queue, executor_config)` and `self.running.add(key)`.
- `execute_async` (line 514): abstract; the concrete executor's "actually launch the task" hook.
- `change_state(key, state, info, remove_running=True)` (line 411): removes the key from `running` and writes `event_buffer[key] = (state, info)` — the canonical results path (helpers `success(key)`/`fail(key)`).
- `get_event_buffer(dag_ids=None)` (line 493): drains (clears) `event_buffer`; the scheduler consumes it in `_process_executor_events(executor, session)` (scheduler_job_runner.py:763), which applies the states to TIs in the DB.
- Slots: `slots_available = parallelism − len(running) − len(queued_tasks)` (or `sys.maxsize` if parallelism 0); `slots_occupied = len(running) + len(queued_tasks)` [source: airflow/executors/base_executor.py:597–607 @ 2.10.5].
- `ExecutorLoader` (executor_loader.py:60): name→path map e.g. `SEQUENTIAL_EXECUTOR → airflow.executors.sequential_executor.SequentialExecutor`, `CELERY_EXECUTOR → airflow.providers.celery.executors.celery_executor.CeleryExecutor`, `KUBERNETES_EXECUTOR → airflow.providers.cncf.kubernetes.executors.kubernetes_executor.KubernetesExecutor`. `get_default_executor` loads the first configured executor from `[core] executor`; `load_executor` supports name, `module.Class`, or `module.Class:Alias` [source: airflow/executors/executor_loader.py @ 2.10.5].
- `SequentialExecutor` (sequential_executor.py:39): `execute_async` appends to `commands_to_run`; `sync()` runs `subprocess.check_call(command)` one at a time and calls `success(key)`/`fail(key)`; single-threaded, works on SQLite [source: airflow/executors/sequential_executor.py:64–94 @ 2.10.5].
- **CeleryExecutor** (2.10.5): lives in the `apache-airflow-providers-celery` provider package (absent from the `apache/airflow` repo at that tag, so its internals are **unverified at source level** here); workers pull from a Celery queue and results return via the Celery result backend; it honors the `BaseExecutor` contract above [source: https://airflow.apache.org/docs/apache-airflow/2.10.5/core-concepts/executor/index.html].

### 1.3 TaskInstance state machine

State enums in `airflow/utils/state.py` @ 2.10.5:

- `TaskInstanceState(str, Enum)` (line 35): `REMOVED="removed"`, `SCHEDULED="scheduled"`, `QUEUED="queued"`, `RUNNING="running"`, `SUCCESS="success"`, `RESTARTING="restarting"`, `FAILED="failed"`, `UP_FOR_RETRY="up_for_retry"`, `UP_FOR_RESCHEDULE="up_for_reschedule"`, `UPSTREAM_FAILED="upstream_failed"`, `SKIPPED="skipped"`, `DEFERRED="deferred"`, plus legacy `SHUTDOWN="shutdown"` ("Not used anymore, kept for compatibility. TODO: Remove in Airflow 3.0"). The enum docstring notes **`None` is also allowed** — a TI created in the DB but not yet scheduled [source: airflow/utils/state.py:35–71 @ 2.10.5].
- `DagRunState` (line 74): `QUEUED`, `RUNNING`, `SUCCESS`, `FAILED` [source: airflow/utils/state.py:74–89 @ 2.10.5].
- Note: **no `awaiting_input`** state at 2.10.5 (that is 3.x human-in-the-loop) [source: https://airflow.apache.org/docs/apache-airflow/2.10.5/core-concepts/tasks.html].

**Transition drivers** (who moves the TI, and how):

| Transition | Actor / mechanism | Evidence (2.10.5) |
|---|---|---|
| `None` (created) | scheduler bulk-creates TIs when a DagRun is created | `DagRun.create_dagrun`; "None is also allowed" enum comment [airflow/utils/state.py:42–44] |
| `None → scheduled` | scheduler `_schedule_dag_run` → `DagRun.schedule_tis` | bulk `update(TI).values(state=SCHEDULED, try_number=case(...))` [airflow/models/dagrun.py:1550–1615] |
| `scheduled → queued` | scheduler critical section | bulk `update(TI).values(state=QUEUED, queued_dttm, queued_by_job_id)` then `executor.queue_command` [scheduler_job_runner.py:640–700] |
| `queued → running` | worker `LocalTaskJobRunner` → `TI.run()` → `_check_and_change_state_before_execution` | `ti.state = TaskInstanceState.RUNNING` (taskinstance.py:2872); `run()` then `_run_raw_task` (3207–3258) |
| `running → success/failed/up_for_retry/skipped/deferred/up_for_reschedule` | worker module-level `_run_raw_task` (taskinstance.py:218) | success: `ti.state = SUCCESS`; `TaskDeferred` → `ti.defer_task(exception)` → DEFERRED; `AirflowSkipException` → SKIPPED; `AirflowRescheduleException` → `ti._handle_reschedule(...)` → UP_FOR_RESCHEDULE; `AirflowFailException`/`AirflowSensorTimeout` → `handle_failure(force_fail=True)`; other exceptions → `ti.handle_failure(e, ...)` (chooses UP_FOR_RETRY vs FAILED) [taskinstance.py:270–340] |
| `up_for_retry → scheduled` | scheduler dependency re-evaluation when `next_retry_datetime` < now | `ready_for_retry` = `state == UP_FOR_RETRY and next_retry_datetime() < timezone.utcnow()` (2687); `next_retry_datetime` = `end_date + delay` with `retry_exponential_backoff` (2643) |
| `running → up_for_reschedule` | sensor reschedule mode | `AirflowRescheduleException`; `BaseSensorOperator` computes next poke interval then raises it (sensors/base.py:251–330) |
| `running → deferred` | operator calls `self.defer(...)` | raises `TaskDeferred` (exceptions.py:405); `TI.defer_task` (taskinstance.py:3188); scheduler can also defer directly via `start_from_trigger` in `schedule_tis` |
| `deferred → scheduled` (resume) | scheduler when the trigger fires / triggerer emits a `TriggerEvent` | "when the trigger fires, its source task is re-scheduled by the scheduler" [docs: deferring]; triggerer side `TriggererJobRunner.run_trigger` (triggerer_job_runner.py:624) — exact DB write not traced line-by-line **(gap)** |
| `running → skipped` (branching) | `BaseBranchOperator` / `@task.branch` → `SkipMixin.skip_all_except` | non-selected downstream TIs marked SKIPPED [airflow/models/skipmixin.py:184 @ 2.10.5] |
| `→ upstream_failed` | scheduler dependency evaluation with `flag_upstream_failed` | `DagRun._get_ready_tis`/`_are_premature_tis` build `DepContext(flag_upstream_failed=True, ...)` (dagrun.py:1043, 1127); `TriggerRuleDep._evaluate_setup_constraint` sets UPSTREAM_FAILED when an upstream failed (trigger_rule_dep.py:281–286) |
| `→ removed` | scheduler when a task vanished from the DAG | `DagRun.task_instance_scheduling_decisions._filter_tis_and_exclude_removed` (dagrun.py:970–972); "Task vanished from DAG before it ran" [utils/state.py:47] |
| clear → back to `None` | UI/CLI `airflow tasks clear` | clearing increments `try_number`, sets `max_tries` to 0 and state to None → task re-runs [docs: dag-run] |
| zombie `running` → failed | scheduler `_find_and_purge_zombies` | `_find_zombies` (scheduler_job_runner.py:2066) selects RUNNING TIs whose `LocalTaskJob` is not RUNNING or has a stale heartbeat; `_purge_zombies` (2089) calls `executor.change_state(ti.key, FAILED, remove_running=True)` [docs: tasks.html zombies] |

**Retry mechanics.** `max_tries = task.retries` (taskinstance.py:1980); `try_number` is the persisted attempt counter; `next_try_number = try_number + 1` (2069); `_try_number` is a deprecated alias (1996–2014). Low-level state writer: `TI.set_state` (2435) → `_set_state` (2409), which also logs, fires listeners, and handles callback requests via `_run_finished_callback` (1539). `refresh_from_db(session, lock_for_update=False)` (2351) reloads the row (optionally `FOR UPDATE`); `refresh_from_task` (2369) copies task attributes. Special exceptions: `AirflowSkipException`, `AirflowFailException` (no retry), `AirflowTaskTimeout`, `AirflowSensorTimeout`, `TaskDeferred`, `TaskDeferralError` [source: airflow/exceptions.py @ 2.10.5].

**Deferral flow (end-to-end, docs-verified):** a running operator calls `self.defer(trigger, method_name, kwargs, timeout)` → raises `TaskDeferred` → TI becomes `deferred` and frees the worker slot → the trigger is serialized into the DB → `TriggererJobRunner` runs `trigger.run()` as an async generator yielding `TriggerEvent` → on fire, the scheduler re-schedules the TI (the worker resumes the operator via `method_name` with `context` + `event`) → worker re-runs the operator. Constraints: triggers must be stateless; kwargs are encrypted at rest since 2.9; `execution_timeout` spans total runtime across deferrals; default triggerer capacity 1000 triggers; the triggerer waits `2.1 × job_heartbeat_sec` before rescheduling triggers from a dead triggerer [source: https://airflow.apache.org/docs/apache-airflow/2.10.5/authoring-and-scheduling/deferring.html; airflow/triggers/base.py @ 2.10.5].

### 1.4 Data flow

**XComs.** Model `airflow.models.xcom.BaseXCom`, table `xcom`, PK `(dag_run_id, task_id, map_index, key)`; `key` is `String(512)`, `value` is `LargeBinary`; FK to `task_instance` with CASCADE; `execution_date` is an association proxy to the DagRun [source: airflow/models/xcom.py:77–140 @ 2.10.5]. Classmethods: `set(...)`, `get_one(execution_date, key=None, task_id=None, dag_id=None, include_prior_dates=False, session)` (317/361/378), `get_many` (434), `clear` (584). TI-level: `ti.xcom_push(key, value, execution_date, session)` (taskinstance.py:3618); `ti.xcom_pull(task_ids=None, dag_id=None, key=XCOM_RETURN_KEY, include_prior_dates=False, session)` (3656) — default key is `return_value` [source: airflow/models/taskinstance.py @ 2.10.5]. Return-value auto-push: `BaseOperator.do_xcom_push` defaults `True`; on completion the return value is pushed under `XCOM_RETURN_KEY` (taskinstance.py:790). Serialization: `BaseXCom.serialize_value` (xcom.py:675) — **pickle if `core.enable_xcom_pickling`, else JSON** (`json.dumps(value, cls=XComEncoder).encode("UTF-8")`); `_deserialize_value` mirrors with `XComDecoder`. **The algorithm in one sentence** (from the `Pregel` docstring, which matches the BSP contract): "Pregel combines **actors** and **channels**… Each step consists of three phases: **Plan** (determine which actors to execute), **Execution** (execute all selected actors in parallel… channel updates are invisible to actors until the next step), **Update** (update the channels with the values written by the actors). Repeat until no actors are selected for execution, or a maximum number of steps is reached." [source: pregel/main.py @ main]. A source comment states it directly: "Similarly to Bulk Synchronous Parallel / Pregel model computation proceeds in steps, while there are channel updates. Channel updates from step N are only visible in step N+1; channels are guaranteed to be immutable for the duration of the step, with channel updates applied only at the transition between steps." [source: pregel/main.py @ main].

### 2.2 Execution machinery

**`Pregel` attributes** (pregel/main.py:758): `nodes: dict[str, PregelNode]` (name → spec); `channels: dict[str, BaseChannel | ManagedValueSpec]` — **`self.channels[TASKS] = Topic(Send, accumulate=False)` is force-added** unless the user supplied one (TASKS is reserved; a non-Topic TASKS raises `ValueError`); `input_channels: str | Sequence[str]`, `output_channels`, `stream_channels`, `stream_mode` (default `"values"`; `StateGraph.compile` overrides to `"updates"`), `stream_eager`; `checkpointer`, `store` (`BaseStore`), `cache`, `retry_policy`, `cache_policy`, `context_schema`, `interrupt_before_nodes`, `interrupt_after_nodes`, `trigger_to_nodes` (channel → nodes it triggers), `node_error_handler_map`, `step_timeout`, `name`, `config`. `auto_validate=True` runs `self.validate()` in `__init__`. There is **no `_algo` attribute / `PregelAlgo` class** on current `main` (older docs referenced one); the algorithm lives in module-level functions in `pregel/_algo.py` plus the `PregelLoop` class in `pregel/_loop.py` [source: pregel/main.py, pregel/__init__.py @ main].

**`PregelNode`** (pregel/_read.py:97) fields: `channels: str | list[str]` — "channels that will be passed as input to `bound`" (a `str` → node invoked with that channel's value; a `list` → invoked with a dict of channel values); `triggers: list[str]` — "if any of these channels is written to, this node will be triggered in the next step"; `mapper: Callable | None` — transforms input before `bound` (e.g. coerce dict → Pydantic/dataclass); `writers: list[Runnable]` — run after `bound`, "responsible for taking the output of `bound` and writing it to the appropriate channels" (cached property `flat_writers` dedupes consecutive `ChannelWrite`s); `bound: Runnable` (default `DEFAULT_BOUND = RunnableCallable(lambda input: input)`); `retry_policy`, `cache_policy`, `timeout`, `tags`, `metadata`, `trace_policy`, `is_error_handler`, `error_handler_node`, `subgraphs: Sequence[PregelProtocol]` (auto-detected via `find_subgraph_pregel(self.bound)`). **No `scoped_writers` on current `main`** — node output → channel writes is handled by the `ChannelWrite` writers and `Command`/`Send` routing [source: pregel/_read.py @ main].

**How `StateGraph.compile()` builds the runtime** (graph/state.py:1177): builds a `CompiledStateGraph(...)` with `channels={**self.channels, **self.managed, START: EphemeralValue(self.input_schema)}`, `input_channels=START`, then `attach_node(START, None)`, `attach_node(key, node)` per node, `attach_edge` per edge, `attach_branch` per conditional edge, and returns `compiled.validate()`. `attach_node` (graph/state.py:1510–1549) constructs:

- **START node:** `PregelNode(tags=[TAG_HIDDEN], triggers=[START], channels=START, writers=[ChannelWrite(write_entries)])`.
- **Regular node:** a dedicated per-node trigger channel `branch:to:{name}` (`EphemeralValue(Any, guard=False)`, or `LastValueAfterFinish` when `defer=True`) is created, and `PregelNode(triggers=[branch_channel], channels=input_channels, mapper=..., writers=[ChannelWrite(write_entries)], bound=node.runnable, ...)`.
- `write_entries` = two `ChannelWriteTupleEntry` mappers: `_get_root`/`_get_updates` (maps the node's returned dict/`Command` into per-state-key writes; only keys in the schema are emitted) and `_control_branch` (maps `Command`/`Send` returns into control writes; `static=_control_static(...)` for declared destinations).
- `attach_edge(start, end)`: appends `ChannelWrite(ChannelWriteEntry(f"branch:to:{end}", None))` to the source node's writers. Multi-source `waiting_edges` create a **barrier channel** `join:{'+'.join(starts)}:{end}` of type `NamedBarrierValue(str, set(starts))` — the end node triggers only after **every** start writes [source: graph/state.py:1551 @ main].
- `attach_branch`: appends `branch.run(get_writes, reader)` (a `ChannelWrite`-registered `RunnableCallable`) to the source node's writers; the selected target is written as `branch:to:{target}` (or `END`, or `Send` → TASKS) [source: graph/state.py:1577 @ main].

**Channels — `update()` semantics** (`BaseChannel` at channels/base.py:19; abstract `get()` "raises `EmptyChannelError` if empty", `update(values) -> bool` "called by Pregel for all channels at the end of each step… returns True if updated", `from_checkpoint`, `checkpoint()`, `consume()`, `finish()`, `is_available()`):

- **`LastValue`** (last_value.py:56–80): single value, **overwrite**. `update` requires **exactly one value per step** (`len(values) != 1` → `InvalidUpdateError`: "At key '{key}': Can receive only one value per step. Use an Annotated key to handle multiple values."); sets `self.value = values[-1]`. `get()` raises `EmptyChannelError` while `value is MISSING` — no initial value until the first write.
- **`Topic`** (topic.py:23): accumulates a `list[Value]`. Constructor `Topic(typ, accumulate: bool = False)` — **no `unique`/dedup parameter on current `main`** (the `Pregel` docstring claiming Topic "can be configured to deduplicate values" is stale). `update`: if `accumulate=False`, clears first (`self.values = []`) then `_flatten`s and extends with the new values — each step's writes **replace** the previous batch; if `accumulate=True`, extends, accumulating across steps. `get()` returns `list(self.values)` or raises `EmptyChannelError`; `checkpoint()` returns the list.
- **`BinaryOperatorAggregate`** (binop.py:65): reducer channel, `BinaryOperatorAggregate(typ, operator)`. `update`: seeds `self.value = values[0]` if never written, then folds: `self.value = self.operator(self.value, value)`; supports an `Overwrite` sentinel (only one per super-step, else `InvalidUpdateError`). **`get()` raises `EmptyChannelError` if the channel was never written** (e.g. a reducer key absent from the initial input).
- **`EphemeralValue`** (ephemeral_value.py:15): "Stores the value received in the step immediately preceding, clears after." `update` with an empty sequence clears the value; with values, `len(values) != 1 and self.guard` → `InvalidUpdateError`; stores `values[-1]`. Used for `START` and `branch:to:` channels, so those triggers fire exactly once.

**The tick/superstep loop.** Loop classes in `pregel/_loop.py`: `PregelLoop` (:158, core), `SyncPregelLoop(PregelLoop, AbstractContextManager)` (:1469), `AsyncPregelLoop(PregelLoop, AsyncAbstractContextManager)` (:1722). Parallel executor: `PregelRunner` (pregel/_runner.py:135), `BackgroundExecutor`/`AsyncBackgroundExecutor` (pregel/_executor.py).

- `Pregel.invoke` (v1 default) delegates to `self.stream(...)`, collecting the last `"values"` chunk; on interrupt it returns `{**latest, INTERRUPT: interrupts}` (v1) or `GraphOutput(value=..., interrupts=...)` (v2). `Pregel.stream` builds `SyncPregelLoop` (or `AsyncPregelLoop` for astream) plus a `PregelRunner`, and drives: `while loop.tick(): ... for _ in runner.tick([t for t in loop.tasks.values() if not t.writes], ...): yield from _output(...); loop.after_tick()`. When `loop.status == "out_of_steps"`, it raises `GraphRecursionError` ("Recursion limit of {config['recursion_limit']} reached without hitting a stop condition") [source: pregel/main.py:2880–3020, 3783 @ main].
- **`PregelLoop.tick()`** — one superstep (pregel/_loop.py:599): (1) **recursion bound** — `if self.step > self.stop: self.status = "out_of_steps"; return False`, where `self.stop = self.step + self.config["recursion_limit"] + 1` (set in the loop `__init__`); (2) **compute next tasks** via `prepare_next_tasks(checkpoint, checkpoint_pending_writes, self.nodes, self.channels, self.managed, config, self.step, self.stop, ...)` — PULL tasks (nodes whose triggers changed) plus PUSH tasks (Sends); (3) **stop if idle** — `if not self.tasks: self.status = "done"; return False` (the null step); (4) re-apply pending writes from a previously interrupted/errored tick (replay path `_reapply_writes_to_succeeded_nodes`); (5) `interrupt_before` breakpoints — `should_interrupt(...)` → `self.status = "interrupt_before"; raise GraphInterrupt()`.
- **`PregelLoop.after_tick()`** — the channel-Update phase (pregel/_loop.py:683): (1) `self.updated_channels = apply_writes(self.checkpoint, self.channels, self.tasks.values(), self.checkpointer_get_next_version, self.trigger_to_nodes)`; (2) emit `"values"` stream output if output channels updated; (3) clear `checkpoint_pending_writes`, flip `is_replaying = False`, save a checkpoint via `_put_checkpoint({"source": "loop"})`; (4) `interrupt_after` breakpoint check → `raise GraphInterrupt()`.
- **`apply_writes`** (pregel/_algo.py:232): sorts tasks by path (deterministic order); `bump_step = any(t.triggers for t in tasks)`; records `checkpoint["versions_seen"][task.name][chan] = checkpoint["channel_versions"][chan]` for each triggered channel; calls `channels[chan].consume()` for read/trigger channels (clears `EphemeralValue`/`LastValueAfterFinish`); groups `task.writes` by channel — reserved pseudo-channels (`NO_WRITES`, `PUSH`, `RESUME`, `INTERRUPT`, `RETURN`, `ERROR`, `ERROR_SOURCE_NODE`) are skipped — then calls `channels[chan].update(vals)` per channel, bumping `channel_versions` via `get_next_version` (default `increment`: int +1). Channels **not** updated this step are still notified with an empty update (`channels[chan].update(EMPTY_SEQ)`) when the step bumped — this is how `Topic(accumulate=False)` clears and `EphemeralValue` resets. If this looks like the tentative last superstep (`updated_channels.isdisjoint(trigger_to_nodes)`), calls `channels[chan].finish()` on every channel (used by `LastValueAfterFinish`/`NamedBarrierValueAfterFinish`).
- **Task scheduling — `prepare_next_tasks`** (pregel/_algo.py:349): **PUSH tasks** consume the `TASKS` channel (`Topic[Send]`): each queued `Send` becomes a task whose input is the Send's `arg`. **PULL tasks**: with `updated_channels` + `trigger_to_nodes` available, the candidate set is the union of `trigger_to_nodes[ch]` for updated channels (sorted for determinism). `prepare_single_task` (:524) creates a PULL task for node `name` only if some trigger channel `is_available()` and `channel_versions[chan] > versions_seen[name][chan]` (or the node never saw it). Task id = hash of `(checkpoint_id, checkpoint_ns, step, name, PULL, *triggers)`. Input = `_proc_input` reading the `PregelNode.channels` keys from live channels; the task's `writes` is a thread-safe `deque` exposed to the node as `CONFIG_KEY_SEND: writes.extend`; metadata includes `langgraph_step`, `langgraph_node`, `langgraph_triggers`, `langgraph_path`, `langgraph_checkpoint_ns`. Result: `PregelExecutableTask(name, input, proc, writes, config, triggers, retry_policy, cache_key, id, path, writers, subgraphs, timeout)` [source: pregel/_algo.py:188, 524, 1260; types.py:667 @ main].
- **Parallel execution — `PregelRunner.tick`** (pregel/_runner.py:176): submits all tasks to a `BackgroundExecutor` (thread pool, or asyncio for `atick`), waits with `concurrent.futures.wait(..., FIRST_COMPLETED)`, commits each finished task's writes via `put_writes` (→ `checkpoint_pending_writes`), and stops/interrupts other tasks on failure ("panic"). **Node output is not applied to channels during the step** — it lands in `checkpoint_pending_writes` and is applied only in the next superstep by `apply_writes` (the map-reduce / BSP contract).

**Recursion limit.** `DEFAULT_RECURSION_LIMIT = int(getenv("LANGGRAPH_DEFAULT_RECURSION_LIMIT", "10007"))` in `langgraph/_internal/_config.py:32`; `ensure_config()` defaults `recursion_limit` to it; `Pregel.stream` rejects `recursion_limit < 1`; exceeding it → `GraphRecursionError` [source: _internal/_config.py @ main; pregel/main.py:2563, 3005 @ main; errors.py:67]. ⚠️ **Docs vs source discrepancy:** the current graph-api doc page claims "Starting in version 1.0.6, the default recursion limit is set to 1000 steps", and the archived 2024 low_level page claimed 25 — the **verified source value (main and released 1.2.11) is 10007**, overridable via the env var [source: https://docs.langchain.com/oss/python/langgraph/graph-api; web.archive.org 2024 snapshot of langchain-ai.github.io/langgraph/concepts/low_level/]. The `step` counter is exposed to nodes as `config["metadata"]["langgraph_step"]`.

**`stream_mode` outputs**: `values` (full state after each step), `updates` (state updates per node, streamed separately), `messages` (LLM token + metadata), `custom` (`get_stream_writer`), `checkpoints`, `tasks`, `debug`; format `version="v1"` (default; raw / `(mode, data)` / `(ns, mode, data)` tuples) vs `version="v2"` (uniform `StreamPart` dicts with `type`/`ns`/`data`) [source: https://docs.langchain.com/oss/python/langgraph/streaming; pregel/_loop.py:1416, pregel/_io.py @ main].

**Checkpointing.** `BaseCheckpointSaver` (libs/checkpoint/langgraph/checkpoint/base/__init__.py:176): `config_specs`, `get`, `get_tuple`, `list`, `put`, `put_writes`, `delete_thread`, `delete_for_runs`, `copy_thread`, `prune` + async twins (`aget`, `aget_tuple`, `alist`, `aput`, `aput_writes`, …); `get_next_version(current, channel)` defaults to int versions incrementing by 1. `CheckpointTuple(config, checkpoint, metadata, parent_config=None, pending_writes=None)`.

- **`Checkpoint`** (TypedDict, :92): `v: int` (format version; **`LATEST_VERSION = 2`** — the field docstring "Currently 1" is stale), `id: str` ("unique and monotonically increasing, so can be used for sorting"), `ts: str` (ISO 8601), `channel_values: dict[str, Any]`, `channel_versions: dict[str, str|int|float]`, `versions_seen: dict[str, ChannelVersions]` (node id → channel versions seen; "used to determine which nodes to execute next"), `updated_channels: list[str] | None`. **No `pending_sends` / `created_at` / `metadata` fields in v1+** — pending Sends live in the checkpointed `TASKS` channel; the timestamp is `ts`; metadata is the separate `CheckpointMetadata`.
- **`CheckpointMetadata`** (TypedDict `total=False`, :38): `source: Literal["input","loop","update","fork"]` ("input" = from invoke/stream/batch input; "loop" = from inside the pregel loop; "update" = manual state update; "fork" = copy), `step` (`-1` for the first "input" checkpoint, `0` for the first "loop" checkpoint), `parents: dict[str, str]`, `run_id`, `counters_since_delta_snapshot`.
- **When/what is persisted:** `PregelLoop.after_tick` → `_put_checkpoint({"source": "loop"})` after **every superstep**; `empty_checkpoint()` creates the initial (input) checkpoint; `create_checkpoint()` snapshots live channels into a new `Checkpoint` (values, versions, versions_seen) [source: pregel/_loop.py:1081, pregel/_checkpoint.py:28, 149 @ main]. Checkpoints are keyed by `config["configurable"]["thread_id"]` and `checkpoint_id` (`CONFIG_KEY_THREAD_ID`, `CONFIG_KEY_CHECKPOINT_ID`, `CONFIG_KEY_CHECKPOINT_NS` in `_internal/_constants.py`). **Subgraphs** checkpoint under their own namespace: `checkpoint_ns = f"{parent_ns}{NS_SEP}{name}{NS_END}{task_id}"` (task-scoped), and `checkpoint_map` maps parent ns → parent checkpoint id [source: pregel/_algo.py:556–590 @ main].
- **`InMemorySaver`/`MemorySaver`**: in-RAM dict-backed; "MemorySaver and InMemorySaver store checkpoints in RAM. When the process restarts, all checkpoints are lost"; class docstring: "Only use `InMemorySaver` for debugging or testing purposes" [source: https://docs.langchain.com/oss/python/langgraph/persistence; checkpoint/memory/__init__.py @ main].

**Dynamic control flow.**

- **`Send(node, arg, timeout=None)`** (types.py:704): "A message or packet to send to a specific node in the graph… used within a StateGraph's conditional edges to dynamically invoke a node with a custom state at the next step." Each Send is written to TASKS and becomes an independent parallel PUSH task next tick (map-reduce) [source: types.py @ main; https://docs.langchain.com/oss/python/langgraph/graph-api].
- **`Command(graph, update, resume, goto)`** (types.py:799): `goto` accepts a node name / `Send` / sequences; `update` is a state update (dict or `(key, value)` tuples); `graph` is `None` (current) or `Command.PARENT` (`"__parent__"`) to navigate a parent graph from a subgraph; `resume` resumes an interrupt. Docs use it in three contexts: returned from nodes, as input to invoke/stream (resume), returned from tools. `map_command` (pregel/_io.py:56) converts an input `Command` to writes at entry: `goto` str → `(branch:to:{name}, START)`; `Send` → `(TASKS, send)`; `resume` → `(RESUME, value)`; `update` → per-key writes [source: types.py, pregel/_io.py @ main; docs graph-api].
- **`interrupt(value)`** (types.py:851): the first invocation in a task raises `GraphInterrupt((Interrupt.from_ns(value, ns),))`; the loop catches it at the superstep boundary, saves the checkpoint + pending writes, and returns control to the caller. Interrupts surface in `updates`/`values` stream as `{INTERRUPT: (Interrupt(value=..., id=...),)}` (the `__interrupt__` key in v1 invoke results), and in v2 as `GraphOutput.interrupts` / `stream.interrupts` [source: pregel/_loop.py:1317–1380, 1416–1469; types.py:851 @ main; https://docs.langchain.com/oss/python/langgraph/human-in-the-loop]. `Interrupt` carries `value` and `id` (default `_DEFAULT_INTERRUPT_ID`, or a hash of the checkpoint ns) [source: types.py:575 @ main].
- **Resume:** call `graph.invoke/stream(Command(resume=value), {"configurable": {"thread_id": ...}})` with the same thread id; the RESUME write feeds the resumed task's scratchpad (`PregelScratchpad.resume` list), and `interrupt()` returns the matched resume value on re-execution. **The node re-runs from the start** ("The graph resumes from the start of the node, re-executing all logic"). Multiple interrupts in one node are matched **by index** against the task-scoped resume list — do not reorder or conditionally skip them [source: types.py:851 @ main; docs human-in-the-loop]. Static breakpoints via `interrupt_before`/`interrupt_after` are checked by `should_interrupt` against `checkpoint["versions_seen"][INTERRUPT]` [source: pregel/_algo.py:155 @ main].

### 2.3 State-machine angle

The official framing: "At its core, LangGraph models agent workflows as graphs… Nodes do the work, edges tell what to do next. LangGraph's underlying graph algorithm uses message passing to define a general program… Inspired by Google's Pregel system, the program proceeds in discrete 'super-steps.' … At the start of graph execution, all nodes begin in an inactive state. A node becomes active when it receives a new message (state) on any of its incoming edges (or 'channels')… At the end of each super-step, nodes with no incoming messages vote to halt… The graph execution terminates when all nodes are inactive and no messages are in transit." [source: https://docs.langchain.com/oss/python/langgraph/graph-api; identical text in the archived 2024 low_level glossary].

- **Static structure, dynamic execution.** The node/edge topology is fixed at compile time: normal edges become `ChannelWrite` writers on source nodes, conditional edges become `BranchSpec` writers whose *selector function* runs at runtime; `Send` produces unbounded dynamic fan-out at runtime; `Command(goto=...)` moves the "next nodes" pointer at runtime. Interrupts pause the run mid-superstep; resume re-enters the loop from the saved checkpoint.
- **Checkpointing = durable state between invocations.** "Checkpointers persist a thread's graph state as checkpoints… a checkpointer 'serves as a fully versioned short-term memory for the graph, allowing it to be paused, resumed, and replayed from any point'" [source: https://docs.langchain.com/oss/python/langgraph/persistence]. The runtime identifies a thread by `thread_id` and a specific run state by `checkpoint_id`; resuming with the same thread id loads the latest checkpoint and `prepare_next_tasks` schedules the next tasks from `channel_versions` vs `versions_seen`. That is exactly the state-machine transition function: (current checkpoint, new input/Command) → next superstep.

### 2.4 Data flow

- **Node input:** resolved through `PregelNode.channels` (alias mapping): `str` → the single channel's value, `list` → a dict of those channels' values (`read_channels`, pregel/_io.py:38); `mapper` coerces to the node's declared input schema (Pydantic/dataclass). `START` sends input via the `START` channel (`EphemeralValue(self.input_schema)`); `TASKS` feeds `Send` args to PUSH tasks.
- **Node output:** a returned dict → per-key writes via `_get_updates` (only keys present in the graph's channel set are written — "a node can write to any state channel in the graph state"); a returned `Command` → `_control_branch` splits `update`/`goto` into state/control writes; `Send` returns → `(TASKS, send)` [source: graph/state.py:1430–1549, 1749–1790 @ main; docs graph-api].
- **Reducer/update semantics per channel** (see 2.2): `LastValue` overwrite (one write per step or `InvalidUpdateError`); `Topic` append with `accumulate` flag (replace-per-step when False, accumulate across steps when True); `BinaryOperatorAggregate` folds `operator(current, update)` with first-write seeding; `EphemeralValue` holds the latest write, clears next step. Docs framing: "Each key in the State has its own independent reducer function. If no reducer function is explicitly specified then it is assumed that all updates to that key should override it"; reducer signature is `(current_value, update) -> new_value` [source: docs graph-api].
- **`StateGraph.compile()` channel construction** (graph/state.py:1815–1944): `_get_channels(schema)` iterates `get_type_hints(schema, include_extras=True)`; per key, `_get_channel`: (1) explicit `BaseChannel` annotation in `Annotated` metadata → that channel (e.g. `Annotated[int, EphemeralValue]` → `EphemeralValue(int)`); (2) last metadata item that is a 2-arg callable → `BinaryOperatorAggregate(typ, meta[-1])`; (3) otherwise → `LastValue(annotation)`. A schema without `__annotations__` (a bare dict) yields a single `__root__` channel. `compile()` then sets `START: EphemeralValue(input_schema)`, `input_channels=START`, `output_channels`/`stream_channels` from the output/state schemas [source: graph/state.py:1177–1404 @ main].
- **Subgraphs:** a compiled graph used as a node; `PregelNode.subgraphs` is auto-populated by `find_subgraph_pregel(bound)`. The parent only passes/accepts shared state keys ("If you pass extra keys… they will be ignored by the subgraph node. Similarly… extra keys returned… will be ignored by the parent graph"); subgraph state checkpoints under its own `checkpoint_ns`; `Command(graph=Command.PARENT, ...)` routes from a subgraph node back to a parent node (multi-agent handoffs) [source: docs graph-api; pregel/_io.py:56 @ main].

## 3. Comparison: Airflow DAG runtime vs LangGraph StateGraph/Pregel

| Dimension | Airflow | LangGraph |
|---|---|---|
| Graph model | DAG (`DAG` + `DAGNode`/`Operator` with `upstream_task_ids`/`downstream_task_ids` sets, topo-sorted, cycle-checked) | StateGraph compiled to a `Pregel` (static topology; per-node trigger channels `branch:to:{name}`, barrier channels `join:{starts}:{end}` for multi-source edges) |
| Runner | `SchedulerJobRunner` loop (DB-driven, durable) | `PregelLoop.tick()` superstep loop (in-process, BSP) |
| Step granularity | A task = one `Operator.execute()`; scheduler heartbeats at `scheduler.heartbeat_sec` | A superstep = one parallel wave of nodes; `recursion_limit` bounds total steps (default **10007** in source) |
| Scheduling decision | Scheduler queries DB for runnable TIs (`_executable_task_instances_to_queued`), respecting deps, pools, parallelism, priority | `prepare_next_tasks`: PULL tasks from trigger-channel versions vs `versions_seen`, PUSH tasks from the `TASKS` channel |
| State representation | Durable DB rows: `DagRun` + `TaskInstance` (state enum) + `XCom` + `Pool` | In-memory `channels` dict snapshot into `Checkpoint` (values + `channel_versions` + `versions_seen`), keyed by `thread_id`/`checkpoint_id` |
| State machine | `TaskInstanceState`: None→scheduled→queued→running→{success, failed, up_for_retry, up_for_reschedule, deferred, skipped, upstream_failed, removed}; transitions driven by scheduler, worker, triggerer | Implicit per-superstep: nodes scheduled from channel writes; interrupts pause the run; there is no per-node state enum — a node is "active/inactive" per superstep |
| Data passing | XCom rows (JSON/pickle, ~48 KB cap), pulled explicitly via `xcom_pull`; TaskFlow auto-wires via `XComArg` | Channel writes: node output dict → per-key writes, applied at the next superstep with reducer semantics (LastValue/Topic/BinaryOperatorAggregate/EphemeralValue) |
| Parallelism | Parallelism via executor + pools + `max_active_tasks` (multiple workers, horizontal) | Parallel within a superstep via `PregelRunner` thread/asyncio pool (vertical, in-process) |
| Control flow | **Static** DAG (branching = runtime decision but structure fixed; no cycles) | Static structure, **dynamic** execution: conditional edges (selector functions), `Send` fan-out, `Command(goto=...)` |
| Retries | `try_number`/`max_tries`/`next_retry_datetime` on the TI row; `up_for_retry`; exponential backoff | Per-node `retry_policy` (task-level retries inside `PregelRunner`) |
| Human-in-the-loop / pause | Deferred tasks via `Triggerer` (`deferred` state, free worker slot) | `interrupt()` / `interrupt_before`/`interrupt_after` — run pauses, checkpoint saved, resume re-runs the node from its start |
| Durability | Whole orchestration is DB-backed; survives restarts; XComs cleared on retry for idempotency | Checkpoints persist per superstep; without a checkpointer, state is lost when the process exits (`InMemorySaver` caveat) |
| Failure semantics | Zombie detection, retries, `upstream_failed` propagation, DAG run rollup from leaf tasks | Superstep "panic": one failed task stops/interrupts sibling tasks; `GraphRecursionError` on step exhaustion |

**Where they converge.** Both are **directed graphs whose node execution is driven by a runner**, not by direct calls: Airflow's scheduler+executor decide which TIs to run based on DB state; LangGraph's loop decides which nodes to run based on channel writes. Both have a notion of **"when is a task/node ready"**: Airflow evaluates `ti_deps` (dependencies + pools + parallelism); LangGraph checks trigger-channel versions. Both are **message-passing systems** in the Pregel sense at the data layer — Airflow's XComs are per-task-keyed writes read by downstream tasks; LangGraph's channel writes are read by triggered nodes — and both defer application of node results: Airflow persists XComs/state before the next task reads them; LangGraph applies writes only at the superstep boundary (BSP: "channel updates from step N are only visible in step N+1"). Both support **dynamic fan-out/fan-in**: Airflow via dynamic task mapping (`expand`) and sensors; LangGraph via `Send` and barrier/join channels. Both model **paused execution**: Airflow's `deferred`/`up_for_reschedule` vs LangGraph's interrupts — in both cases the worker/slot is freed and execution resumes later (Airflow: DB + triggerer; LangGraph: checkpoint + resume input).

**Where they fundamentally differ.** Airflow is a **batch, durable, DB-centric orchestration engine**: every state transition is a committed DB row, the graph is acyclic and static, retries and failure propagation are first-class, and the scheduler is an external process heartbeat-looping against a shared database — safe to run many schedulers with a critical-section lock. LangGraph is an **in-memory, interactive state machine**: the graph is compiled into a `Pregel` object, nodes are Python callables executed in a single process, state is a typed dict over channels, and BSP supersteps make parallelism and determinism the core model. Airflow's scheduler runs at human/batch timescales (seconds–minutes) with unbounded wall-clock durability; LangGraph's loop runs at sub-second interactive timescales bounded by `recursion_limit`, and its durability is opt-in via a checkpointer. Airflow's control flow is fixed at DAG-parse time (branching is data-dependent but the *shape* is static); LangGraph's control flow is decided at runtime (`Send`, `Command`), including cyclic and dynamic graph navigation that Airflow's acyclic DAG forbids. XComs are durable shared rows with an explicit pull API; LangGraph channels are transient unless checkpointed, and writes flow by superstep broadcast rather than by explicit pull.
